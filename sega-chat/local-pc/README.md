# Локальная папка — заготовка, не готовая функция

Этот каталог пока не подключён к мессенджеру и не устанавливает программу на ПК.
`folder.js` — только основа для будущего помощника: просмотр выбранной папки и
чтение файла небольшими частями. Она не принимает сетевые запросы, не создаёт,
не меняет, не удаляет и не синхронизирует файлы.

Предусмотрены относительные пути, отказ от переходов `..`, Windows-имен устройств,
альтернативных потоков, а также исключение символических ссылок и junction внутри
выбранной папки. Корень берётся только из локального выбора пользователя. Список
и чтение ограничены по размеру. Модуль НЕ является законченной границей
безопасности: локальный процесс может подменить путь между проверкой и открытием,
а Windows junction/reparse points и гонки нуждаются в проверке на Windows 10.
Не подключать к сети, пока эти риски не устранены и не проверены.

Следующие обязательные части: управляемое пользователем подключение и отзыв
конкретного устройства; защищённый обмен с проверкой личности обоих концов,
чтобы посторонний не получил доступ, а сервер не получал содержимое в открытом виде; понятный статус
«компьютер выключен»; просмотр, передача и запись файлов без обхода выбранной
папки; проверка на настоящей Windows 10 и тесты отказов и перезапусков. Нельзя
выдавать демонстрационный раздел за работающий локальный диск. При обычном
скачивании в браузер требуется согласие пользователя. Автосинхронизация двух
ПК — отдельная, явно включаемая возможность; обработка одновременных изменений
и удаления должна сохранять данные и быть согласована с владельцем.

Проверка заготовки: `node test/local-pc-folder.mjs` из каталога `sega-chat`.
Проверки не заменяют запуск на Windows и не проверяют сеть или синхронизацию.


## Информационный раздел в окне подключения дисков

В рабочей ветке в `public/app.js` добавлен видимый раздел «Мои локальные диски»
в существующее окно подключения дисков. Он прямо говорит, что функции, установки
и отправки заявок пока нет; кнопка запроса отключена и не вызывает API. В
раскрывающемся описании объясняются будущие разрешение администратора, отдельное
включение синхронизации, корзины и конфликты. Это не работающая заявка, не
инструкция установки и не доказательство выполнения перечисленного. Проверено в
jsdom, не на реальном телефоне/браузере. Ветку ещё не выпустили и пользователю
ничего устанавливать не нужно; на установленном pkg3-153 раздела нет. Кэш статики
в ветке поднят до `sega-static-v148`; в установленном выпуске остаётся v147.

## Связка снимков и обзора группы — проверка на фальшивых данных

`test/local-pc-multi-snapshot-flow.mjs` собирает кандидаты снимков из данных в
памяти и передаёт их в анализ группы и обзор удалений: четыре условных ПК и
одно условное облако (отдельно для Google и Яндекса), изменение, удаление,
конфликт правки с удалением каталога, смена имени, неполный снимок и отсутствие
участника. Появление нового пути откладывает возможное удаление. Состояние сети,
база и полнота искусственно заданы тестом; модель не доказывает ни историю
переименования, ни идентичность объектов, ни правильность реальных данных.
Тест не переносит файлы, не обращается к облакам и не выполняет операции корзины.

## Разрешение администратора — лабораторный этап

Владелец потребовал, чтобы пользователь мог запросить подключение личной
папки кнопкой с понятным объяснением; администратор должен получить запрос и
разрешить или отклонить функцию. Одобрение функции не является согласием на
автоматическую синхронизацию и не даёт другим пользователям права на файлы.

В отключённом экспериментальном API (`experimental-api.js`) модель заявки
привязана к вошедшей учётной записи; по умолчанию владельцу и агенту устройства
доступ запрещён, включая ранее зарегистрированные устройства. Администратор
видит список ожидающих и одобренных запросов, может одобрить, отклонить или
отозвать разрешение. Каждая новая заявка имеет уникальный ID, старое решение не
применяется к новой заявке. При отзыве экспериментальные ключи подключений
удаляются из актуальной записи, а старые устройства не оживают после повторного
разрешения. Отзыв своих устройств доступен владельцу и без разрешения. Это
лабораторный API, который не включён в обычном сервере и не подключает файлы.
Проверки API не заменяют будущую сквозную защиту всех настоящих интерфейсов,
процессов и облачных операций; пользователь/администратор определяются сервером,
а не полями тела запроса. При повреждённом состоянии разрешения хотя бы у
одного пользователя административный список возвращает 503 целиком, а не
показывает неполные списки как достоверные; при решении по повреждённой записи
тоже возвращается 503, а не ошибочный 409 об устаревшей заявке. Запись не
исправляется и решение не сохраняется автоматически.
При сбое сохранения память может уже измениться, хотя клиент получил 503;
лабораторный запрос, включая чтение списка, повторно пытается записать базу до
ответа. В тесте отказавший диск не выдаёт успешный список до восстановления
записи. Убирать эту запись ради опроса без иной гарантии подтверждённого
состояния нельзя. После сбоя питания старая запись может восстановиться.
Внешний агент, уже исполняющий действие, не обязательно остановится. Нужны
надёжный журнал, отказоустойчивое хранение, аудит и настоящие тесты безопасности.

`access-request-view.js` — отдельное неподключённое окно с объяснением и кнопкой
«Запросить подключение моей папки», отображением состояний и отказом от повтора
до проверки после неоднозначного ответа. Это только jsdom-прототип; обращения
должны предоставляться извне. `admin-access-view.js` и CSS — отдельный
неподключённый черновик: список заявок и уже разрешённых пользователей,
кнопки «Разрешить»/«Отклонить», явное обновление списка, различение людей по ID,
безопасное текстовое отображение и запрет повтора по старому списку. Это окно
не отправляет уведомления и пока не содержит кнопку отзыва. Тест двух окон с
лабораторным API в памяти проверяет устаревшее решение; проверки прав по-прежнему
обязаны выполняться на сервере, независимо от интерфейса. Закрытие сообщает
отмену вызывающему коду, но уже отправленное решение может исполниться.

`admin-request-monitor.js` — неподключённый лабораторный наблюдатель списка
ожидающих заявок для будущего индикатора при открытом приложении. После явного
`start` он выдаёт число заявок, а новые номера считает только после первого
успешного снимка; повтор той же заявки не создаёт нового события. При ошибке
состояние «неизвестно», а не ноль, пауза между попытками увеличивается; нет
параллельных запросов и автоматических решений. `stop` отменяет сигнал и сбрасывает
память. Если внешняя зависимость игнорирует отмену, повторный запуск ждёт её
завершения; оболочка должна сбрасывать индикатор при остановке/смене сессии и
передавать работающий с отменой клиент. Автоматический опрос — не чаще раз в 30 секунд, по умолчанию раз в минуту;
ручное `refresh` можно вызвать чаще. Лабораторный API при каждом запросе переписывает базу:
для VPS эта схема не готова и не прошла нагрузочные испытания. Начальный снимок
показывает все ожидающие заявки, но не выдаёт отдельные события «новая»; учёт
номеров живёт только в памяти. При закрытом приложении опроса нет. Это НЕ push,
НЕ доставка уведомления и НЕ интеграция в мессенджер. В VM проверены дубликаты,
ошибки, остановка и перезапуск; в jsdom + локальном TLS проверено изменение числа
по настоящим лабораторным заявкам. Реальный браузер, фоновые уведомления,
перезапуск VPS, долговечность и права не доказаны.

`admin-request-indicator.js` и CSS — отдельный неподключённый jsdom-черновик
отображения наблюдателя: число относится к последней проверке, при обнаруженном
сбое число неизвестно, есть ручное обновление и колбэк открытия списка. Создание
не запускает опрос, для него нужен явный `start`; `stop`/`dispose` очищают
показания и отменяют ожидающие действия. Хозяин обязан остановить и удалить
компонент при выходе/смене сессии, использовать новый клиент для новой сессии
и самостоятельно закрыть открытое окно. Отмена не отменяет уже открытое окно или
серверное действие, если обработчик не поддерживает сигнал. В jsdom с локальным
TLS кнопка открывала экспериментальное окно, счётчик менялся после заявки и
решения; не-администратору список недоступен. Это не пользовательский интерфейс
мессенджера, не уведомление в фоне и не Web Push; состояние может устареть между
опросами, нагрузка и поведение настоящего браузера не проверены.

`admin-session.js` — неподключённая лабораторная сборка индикатора и одного
окна решений под один токен. Запуск явный; при `dispose` останавливает опрос,
сигнализирует отмену, очищает окно и DOM. Перед запросом и после ответа сверяет
исходный токен; при обнаруженной смене очищает интерфейс, а новый вход требует
нового экземпляра. `checkSession` позволяет оболочке проверить смену, но не
является наблюдателем за входом: если токен поменялся между запросами, старые
данные остаются видимы до вызова `dispose`/`checkSession` или следующей проверки.
Будущая оболочка обязана немедленно вызывать `dispose` при выходе, смене сессии
и потере роли; смена роли при неизменном токене сама здесь не обнаруживается.
Проверка администратора всегда на сервере. Отмена не откатывает решение, уже
доставленное серверу. jsdom тестирует остановку при ожидании и поздние ответы;
jsdom с локальным TLS — смену токена администратора на пользователя и отказ
сервера не-администратору. Реальные браузерные события и отзыв прав не проверены;
это не рабочая интеграция и не гарантия уничтожения всех копий данных в памяти.

`access-http.js` — неподключённый HTTPS-клиент для обоих окон и лабораторного
API: только origin открытой страницы, привязка экземпляра к одной сессии,
ограничение размера ответа и срока ожидания, запрет перенаправлений и повторной
автоматической отправки решений. При потере ответа результат может уже быть
записан, окно требует обновить список. Закрытие/сигнал останавливает ожидание,
но не откатывает действие на сервере. В jsdom с Node fetch и общедоступным
тестовым TLS-сертификатом проверены оба окна, реальные лабораторные сессии,
отказ не-администратору, одобрение и отклонение, потерянный ответ после записи,
перезапуск тестовой БД, отказ непроверенному сертификату и перенаправлению.
Это не настоящий браузер или пользовательский сервер; прототип не доставляет
уведомлений и не интегрирован в продукт. Лабораторное сохранение переписывает
базу при каждом лабораторном запросе — нагрузка не измерена и для VPS не годится
без переработки и тестирования. Токен нельзя передавать через недоверенные
обработчики; HTTPS не защищает от сервера, который подменил клиентский код.
В рабочей ветке есть только отключённая кнопка; работающей кнопки, административного экрана,
доставки уведомления администратору или проверки прав на реальных файлах; всё это
ещё надо создать и проверить. Лабораторный API
пока допускает решения всех учётных записей `isAdmin`, а не только одного
определённого владельца; уточнить это у владельца до настоящего подключения.
Лабораторное ограничение учётной записи увеличено до 32 неотозванных записей,
включая незавершённые подключения. При этом реле позволяет одновременно загрузить
не более 100 устройств для всех пользователей и ограничивает общий объём пакетов
в памяти до 8 МиБ (это не предел всего потребления памяти). Глобальный предел
может остановить добавление устройства, даже когда у пользователя есть слоты;
нет очереди ожидания и справедливого распределения, производительность не измерена.
Лимиты 32/100 — ограничения прототипов, не обещание вместимости конечного продукта.
Пять фиктивных устройств проверены по локальному HTTP, шифрованные запросы,
изоляция и отзыв; настоящая синхронизация, облака и Windows не проверены.
Тесты заявки, решения, отказа, отзыва, перезапуска,
сбоя сохранения, устаревшего решения и UI не являются доказательством готовности.

## Согласованные требования (пока не работают в программе)

- Синхронизация в обе стороны включается человеком явно.
- Переименование файла или папки на одном участнике должно отражаться на
  остальных синхронизированных ПК и подключённом облаке. При конфликтующих
  именах или одновременных изменениях нельзя незаметно потерять данные. Это
  требование пока не реализовано; перемещения и поведение офлайн ещё не уточнены.
- При удалении файл или папка должны попасть именно в системную корзину Windows
  на обоих ПК, без безвозвратного удаления. Если корзина недоступна, удаление
  нужно остановить и показать ошибку. Замена файла тоже требует сохранения
  прежней версии: ни одна версия не должна незаметно исчезнуть.
- Одновременные изменения одного файла должны сохранять обе версии. Изменение
  папки на одной стороне одновременно с удалением на другой — конфликт, а не
  разрешение на стирание изменённой папки.
- Завершённые файлы/папки — зелёная галочка; незавершённые — круговая стрелка,
  принудительный запуск для каждого элемента и всего окна. При отсутствии
  интернета на кнопках «Нет соединения». Показывать «идёт» только когда работа
  действительно выполняется; отдельное состояние для недоступного второго ПК.

## Уточнение: несколько ПК и облако

Владелец попросил синхронизировать одну папку между двумя, тремя, четырьмя и
более ПК, а также с папкой Google Диска или Яндекс Диска. Прежний двухсторонний
`sync-plan.js` не обеспечивает согласованность общей группы: нельзя просто
запускать его попарно и объявлять результат общей синхронизацией.

`multi-sync-analysis.js` — отдельная неподключённая модель анализа в памяти, не
план выполнения: для фиксированной группы из 2–32 участников с предполагаемой
общей подтверждённой базой она лишь перечисляет изменённые пути и конфликты.
Участники обозначаются как ПК, Google или Яндекс, но реальных облачных адаптеров
здесь нет. Модель требует явных флагов связи, полноты всех снимков и общей базы;
флаги не доказывают полноту, актуальность, принадлежность базы группе или даже
существование участника. При недоступном участнике она отказывается от анализа,
а не удаляет файлы. Изменение папки на одном участнике одновременно с удалением
папки на другом отмечается конфликтом; в `changedBy` указываются и участники,
изменившие вложенные элементы. Совпадение хешей не доказывает истории.
Модель не описывает исполнение, не сохраняет версии, не синхронизирует файлы и
не устанавливает корзину облака. Ограничение 32 — только предел прототипа, не
согласованное ограничение конечного продукта.

Необходимы отдельная архитектура группы и истории для отключённых устройств,
подключение/удаление участников, начальное объединение, безопасная запись и
восстановление, защита от несвежих данных, API/особенности и права обоих облаков,
их корзины и сохранение конфликтов, проверки на реальных устройствах и аудит.
Владелец уточнил: при удалении файла/папки на одном ПК соответствующие объекты
должны попадать в корзины всех остальных ПК и подключённых Google/Яндекс дисков,
без автоматического безвозвратного удаления. Срок хранения корзины облака и
другие ограничения провайдера ещё предстоит выяснить; обещать бесконечное
хранение нельзя. Нельзя переносить
старые гарантии двухстороннего плана на группу или выполнять этот анализ как
план. Тесты только на фиктивных снимках в памяти.

`multi-rename-review.js` — отключённый обзор переименований, не исполнение.
На фиктивных снимках со стабильными *предположительно общими* ID объектов
распознаёт смену имени файла или папки и проверяет состав всего её поддерева;
различные имена, изменение содержимого, исчезновение, занятое имя или подмена
отмечаются конфликтом. Простое отсутствие и совпадение хешей не доказывают
переименование. Для обзора нужны включение, предполагаемая общая база, полный
снимок каждого доступного участника; изменение только регистра и перенос в
другую папку консервативно отмечаются конфликтом. Это ограничения модели, не
согласованное поведение готовой функции. Предел модели — 2000 элементов в
каждом снимке и 32 участника. На практике стабильных общих ID и достоверных
снимков ещё нет; флаги не доказывают их, проверка не предотвращает гонки после
расчёта. Отдельный `multi-sync-analysis.js` может трактовать смену пути как
отсутствие старого и появление нового. Никакой из черновиков нельзя использовать
для настоящих переименований или удаления. Тесты используют условные четыре ПК,
Google и Яндекс в памяти, не реальные API.

`multi-change-review.js` — пробная совместная сводка переименований и удаления.
Если распознано хотя бы одно переименование, даже конфликтующее, все кандидаты
удаления откладываются для разбора. Если на прежнем пути обнаружен другой
условный objectId (даже при совпадении содержимого), совместная сводка также
откладывает все кандидаты удаления, включая несвязанные. Отдельный обзор удаления
не учитывает ID. Обзор удаления также откладывает их при любом
новом пути, даже не связанном с удалением; это временное консервативное правило,
а не пожелание к готовому продукту. Тесты охватывают смену имени файла и дерева,
занятое старое имя, разные имена, замену ID при том же содержимом,
неподтверждённую идентичность и несвязанные изменения. Общие ID, полнота и история по-прежнему лишь предполагаются, а
простое отсутствие без добавлений всё равно не доказывает удаление. Даже при
пустом списке конфликтов сводка не является разрешением для настоящих операций;
другие модели напрямую не используют эту сводку.

`multi-trash-review.js` — обзор в памяти: на основании условно подтверждённой
общей базы и полных снимков перечисляет пути с отсутствующей копией, участников
с копиями и конфликты. Удалённая папка рассматривается целиком, а не как
независимые дочерние удаления. При изменённом поддереве — конфликт; при любом
новом пути все кандидаты удаления консервативно откладываются как конфликт. Обзор не
доказывает, что отсутствие возникло именно из-за удаления и что объект был
помещён в корзину; это не план операций и не право удалять. Устаревшие снимки,
смена группы, пропавшая история, гонки и неполные данные могут привести к ложным
выводам. `createDeletionRecheck` сохраняет в памяти копию условной базы, состава
и сводки, затем пересчитывает её по новым данным: отказывает при другом составе,
базе, пропавшей копии, изменении дерева или недоступности участника. Изменение
порядка участников также консервативно отвергает сводку. Модель не отслеживает
события, а флаги полноты передаются снаружи: неполный список, ошибочно объявленный
полным, не отличить от удаления, что показано тестом. Идентичный снимок не
исключает подмены или изменений после проверки. Повторная проверка НЕ разрешает
реальную операцию. Реального исполнения, облачной/Windows корзины и защиты нет.

Общие HTTP-клиенты `lib/gdrive.js` и `lib/yadisk.js` теперь отвергают
оборванный ответ после заголовков или части тела; даже полный на вид JSON в
незавершённом теле не подтверждает действие. Для удаления это неопределённый
исход с предложением проверить состояние вручную, без автоматического повтора.
Тест на локальном фальшивом HTTP проверяет обрывы ответов Google, начала и
статуса операции Яндекса, chunked-ответ и ограничение размера. Эти HTTP-клиенты
используются и другими обычными облачными маршрутами — изменение шире локального
диска, оно ещё не выпущено и не проверено на настоящих сервисах. Помимо таймаута
бездействия теперь есть таймер общего ожидания ответа (обычно 10 секунд, при
опросе Яндекса 2 секунды): медленно поступающие байты не продлевают ожидание.
Это ограничение может прервать и корректный, но долгий ответ; точность зависит
от доступности цикла событий. Локальная заглушка проверяет медленный поток и
успешный ответ до срока. Никаких гарантий доставки,
согласованности или фактического попадания в корзину тест не даёт.

После ручного переименования Google сервер теперь возвращает путь с номером
того слота, с которым выполнялась операция. Раньше результат второго диска
ошибочно получал префикс первого; последующее открытие могло использовать не тот
токен. На локальной HTTP-заглушке проверены первый, второй и третий слоты,
использование их токенов и открытие пути из ответа. Настоящие Google Диски не
проверялись; исправление не выпущено и не является синхронизацией.

Ручное переименование Яндекс Диска теперь отвергает исходный и целевой пути
из разных слотов, а также номера слотов вне 1–3 — до запроса к облаку. Иначе
удаление номера из адреса могло привести к изменению исходного диска с ответом,
указывающим другой диск. Переименование внутри одного слота сохраняется; это
не перенос между дисками. Серверный маршрут и адаптер проверены локальной
заглушкой, реальные Яндекс Диски не проверялись. Изменение ещё не выпущено.

Ручное переименование облака в этой ветке также проверяет подтверждение:
Google должен вернуть запрошенные ID и имя, а Яндекс при 202 — подтверждённый
статус асинхронной операции, не только факт её начала. Ссылка статуса проверяется
по тому же origin и разрешённому пути; автоматического повтора переименования
нет. Потерянный, неоднозначный или слишком долгий ответ сообщает, что нужно
проверить состояние перед повтором. Яндекс 201 считается завершением согласно
документации. Это изменение обычных ручных операций, ещё не выпущено. Локальные
HTTP-заглушки и тесты API приложения не доказывают работу настоящих сервисов,
идентичность файлов, отсутствие гонок или групповую синхронизацию. При длинной
асинхронной операции ограниченный опрос может дать неопределённый результат,
хотя операция впоследствии завершится. Документация:
https://yandex.ru/dev/disk-api/doc/ru/reference/move и
https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update.

Проверка существующего кода облачных дисков на фальшивом HTTP-сервере:
`yadisk.removePath` отправляет `permanently=false`, `gdrive.trashPath` —
`trashed:true`. Это существующие ручные функции, не подключённые к группе.
В текущей ветке общая ручная функция Яндекса при HTTP 202 проверяет адрес статуса
на тот же настроенный origin и разрешённый путь операции, а затем ограниченно
опрашивает статус; успех только при `success` или первоначальном HTTP 204.
Три опроса с паузой 250 мс и общим таймером 2 секунды на каждый запрос; это
не строгий общий срок всей операции. При долгом ожидании, ошибке, подозрительном адресе или
потере связи исход неизвестен, повторно отправлять удаление автоматически нельзя.
Реальный Диск не проверен. Ссылки в документации Яндекса: `https://yandex.ru/dev/disk-api/doc/ru/reference/delete`
и `https://yandex.ru/dev/disk-api/doc/ru/reference/operations`. В текущей ветке
обычная ручная операция Google теперь требует в ответе совпадающий `id` и
`trashed:true`; при неверном ответе, сетевом обрыве, 5xx или перенаправлении
возвращается неопределённый результат и предложение проверить файл и корзину,
автоматического повтора нет. Это изменение общей функции `lib/gdrive.js`, а не
готовая синхронизация; оно ещё не выпущено и реальный Google не проверен.
Даже подтверждённый ответ `ok` НЕ доказывает согласованность всей группы и не
подходит для фиксации общей базы. Правильная идентичность и размещение объекта,
права, папки/вложенные изменения, результат корзины, асинхронные запросы и
потеря ответа требуют безопасного механизма и реальных проверок, прежде чем
запускать хоть какое-либо удаление в синхронизации.

`sync-plan.js` только рассчитывает предварительные операции на основе полных
проверенных списков и последней подтверждённой общей базы. Не выполняет их.
План и кандидат общей базы теперь отклоняются, если не передано явное включение
синхронизации, наличие связи и полнота списков; для плана также необходимо
подтверждение общей базы. Одни эти флаги не доказывают, что сведения актуальны
или действительно полны. В предварительном плане удаления записывается, с какой
стороны отсутствует элемент, а для папки — ожидаемый состав всего поддерева.
Список операций ещё НЕ содержит всех гарантий для безопасного исполнения:
перед переносом папки в корзину заново надо надёжно проверить весь её состав и
отсутствие на другой стороне, а перед заменой/удалением — состояние обоих файлов.
`isPlanActionCurrent` повторно рассчитывает план из переданных снимков и ищет
точное совпадение операции, отклоняя конфликты и устаревшие описания. Это лишь
проверка модели: переданная база должна быть той же доверенной базой, а новые
снимки и признаки связи должны быть действительно актуальными и полными. Даже
совпадающее содержимое не доказывает неизменную идентичность файла, а после
проверки состояние может измениться. Нельзя использовать результат как право
на корзину, запись или публикацию; безопасного исполнителя пока нет.

`planInitialSync` моделирует отдельное первое подключение с явным подтверждением
новой пары и отсутствия предыдущей базы. Исходные файлы только на одной стороне
предлагается скопировать, а разные файлы с одинаковым именем или файл вместо
папки — конфликт. Начальный план дополнительно запрещает удаление и замену;
это не фактическое сохранение обеих версий и не работающая синхронизация.
`isInitialPlanActionCurrent` сверяет предложение с повторным расчётом; она тоже
не разрешает реальную запись. Флаги передаются извне и не доказывают, что это
первое подключение. Потерю или повреждение существующей истории нельзя
автоматически считать первым подключением или подтверждённой пустой базой:
нужны надёжное хранение и восстановление истории. Первую общую базу можно
рассматривать только после фактического безопасного разрешения конфликтов,
завершения действий и проверки обеих сторон; сейчас этого исполнителя нет.

Нужны устойчивый журнал, атомарное восстановление после сбоя, правила имён
конфликтных копий и настоящая интеграция с корзиной Windows. Сам по себе расчёт
не является защитой от гонки. При неполном списке или потере связи планировать
удаление нельзя. Обновлять общую базу можно только после повторной проверки
фактического состояния обеих сторон. Для больших списков сравнение удалённых
поддеревьев использует индекс, а не полный повторный обход для каждой папки.
Важно: обычные списки `folder.js`/`windows-safe-folder` не являются доказательством
полноты для синхронизации. В частности Windows-черновик пропускает ссылки,
неподдерживаемые и недоступные элементы; пропуск нельзя считать удалением.
В неподключённом Windows-черновике добавлен отдельный `listFailOnSkipped`,
который вместо известных пропусков должен выдавать ошибку. Он НЕ создаёт
атомарный снимок и не доказывает полноту: содержимое может меняться во время
перечисления или сразу после него. Реальное Windows-поведение не проверено.
Для синхронизации нужны достоверные полные снимки, явные ошибки и повторная
проверка всего дерева, иначе удаление может затронуть реальные данные.

`snapshot-candidate.js` — отдельный лабораторный эксперимент с поддельным
источником: два обхода, контроль заявленных меток, чтение каждого файла кусками
и хеш его байтов. Отменяется при ошибке, изменении списка/метки, неполном
чтении и превышении лимита. Сигнал отмены также прекращает ожидание зависшего
перечисления или чтения, но не гарантирует прекращение работы источника; поздний
ответ не становится снимком. Если источник игнорирует сигнал, вызывающая сторона
не должна считать его остановленным или бездумно запускать повторный обход.
Проверено на заглушках, не на Windows. Требует отдельный контракт поставщика, который ни
`folder.js`, ни Windows-мост сейчас не реализуют. Флаг полноты и метки сообщает
сам источник — модуль не доказывает их достоверность; даже два прохода не делают
снимок атомарным. Файл или папка могут измениться во время обхода или после него,
а некоторые подмены могут остаться незамеченными. Результат нельзя считать
подтверждённым списком для синхронизации, назначения базы или удаления; реальные
файлы/Windows и защита от гонок не проверены. Эксперимент не подключён к сети.

`confirmSyncBase` — чистая проверка *кандидата* общей базы: синхронизация должна
быть включена, оба ПК доступны, обе проверки полными, все действия завершены, а содержимое снимков
должно совпадать. Флаги передаёт вызывающий код; сама функция не доказывает их
достоверность и не сохраняет базу. Настоящие проверка полноты, разрешение
конфликтов, журнал, безопасное атомарное сохранение и восстановление ещё нужны.

`conflict-name.js` — отдельный черновик подбора имени второй версии файла
при одновременных изменениях. На основании переданных списков имён с обоих ПК
он предлагает имя вида «отчёт (другая версия).txt», не создавая файлов и не
меняя исходники. Учитываются похожие имена, максимальная длина и расширение.
Переданные списки могут быть неполными или устареть; сравнение имён в JavaScript
не повторяет в точности правила Windows (в частности, короткие имена). Настоящий
исполнитель обязан проверять состав на обоих ПК, использовать исключительное
создание без перезаписи и безопасные дескрипторы, заново проверять версии,
сохранить и подтвердить вторую копию на обоих ПК до любого изменения оригинала,
а также надёжно запоминать выбор сторон и восстанавливать все шаги после сбоя.
Никакой исполнитель, настоящая запись или разрешение конфликтов пока не сделаны.
`suggestGroupConflictNames` — неподключённый расчёт для 2–32 условных участников:
для каждой различной заявленной пары хеш/размер предлагает уникальное имя с учётом
всех переданных списков. Версия первого ID по сортировке условно получает исходное
имя для воспроизводимости, а не как решение о перезаписи реальных файлов; источник
каждой версии указан в результате. Требуются флаги доступности и полноты, исходный
файл во всех списках; неоднозначные имена в одном списке отвергаются. Это только
переданные утверждения — проверка не доказывает полноты, содержимого или прав;
изменение имён после расчёта и особенности Windows/облака могут создать коллизию.
Тестированы четыре фиктивных ПК и два облака, 32 разные версии и порядок входа;
никакие файлы, Windows или реальные облака не затрагивались. Конфликты удаления
с изменением и конфликты файла с папкой этим подбором не разрешаются и по-прежнему
останавливают соответствующее поддерево.

`sync-status.js` — модель отображения; она не измеряет сеть и не знает
состояния реальных файлов. Без явно включённой синхронизации модель не
показывает галочку и не предлагает запуск. Для каждой строки и всего окна
предусмотрены отдельные состояния и кнопки. При переданных допустимых числах во время работы показывается
процент переданных данных; 100% передачи ещё не означает зелёную галочку.
Общий процент должен измерять исполнитель: модель не выводит его из неполных
данных отдельных строк. Галочка требует отдельного подтверждения всей проверки
и каждого элемента, в том числе для пустого списка. `syncTreeStatuses` считает
предварительные состояния всех вложений: папка не получает галочку, если один
из переданных потомков не завершён или не проверен. Несвязные папки сохраняют
свой независимый статус; при одновременной работе в поддереве кнопка повтора
этого поддерева/общего окна не предлагается. Прогресс папки не вычисляется из
прогресса отдельного файла. Для зелёной галочки также нужно явно передать признак
полного дерева. `syncItemStatus` отдельно не выдаёт галочку папке без её дерева.
Эти функции не проверяют наличие всех файлов, свежесть списка или настоящую
синхронизацию: переданные флаги и статусы могут быть ошибочными. Принудительный повтор не
должен разрешать конфликты перезаписью, обходить корзину или другие проверки.
Интерфейс, измерение прогресса и сами кнопки ещё не подключены.

Проверки: `node test/local-pc-sync-plan.mjs` и
`node test/local-pc-sync-status.mjs`. Они не проверяют корзину Windows, связь,
визуальное оформление, сохранение копий и передачу файлов.


## Эксперимент с зашифрованным чтением

`owner-read-client.js` — неподключённый клиентский заготовочный код для Node и
браузера. Создаёт случайный номер, шифрует запрос списка, части или отметки файла и
проверяет ответ по ключу, номеру, направлению и сроку; затем проверяет структуру,
имена, размер, кодировку байтов и версию. Один запрос не принимает два разных
ответа. Модуль ничего не отправляет, не подтверждает и не сохраняет. Он не
подтверждает содержимое целого файла и не доказывает полноту списка. Настоящий
код обязан проверять ответ до `ack`, отдельно проверять весь файл и спрашивать
«Скачать файл на устройство?» до сохранения, кроме явно включённой синхронизации.
Доступ к настоящим файлам запрещён.

`owner-read-transport.js` — неподключённая модель последовательности обмена,
а не готовый сетевой транспорт: адреса, HTTP, вход, сроки сетевых вызовов и их
ограничения ей должен обеспечить вызывающий код. Запрос создаётся один раз;
после неопределённой ошибки вызывающий код может повторить его с тем же номером
и пакетом. Ответ проверяется до `ack`; при неопределённом результате вызывающий
код может повторить `ack` без повторного чтения. Выданные результаты копируются, один запрос не выполняется
параллельно. Автоматических повторов, сохранения состояния, загрузки и UI нет.
Отмена проверяется до и после вызовов, но не останавливает обработчик, который
её игнорирует; действие на сервере могло выполниться. При истечении срока,
перезапуске/отзыве или потере памяти повтор может быть невозможен: очередь и
отметки relay не сохраняются. Проверка части не подтверждает весь файл или
полноту папки. Тесты моделируют потерянные ответы и подмену в памяти, а также
локальный HTTP с тестовыми обработчиками и TLS агента, не настоящий браузер.

`owner-http.js` — отдельный неподключённый лабораторный обработчик сети для этой
модели. Использует только HTTPS и origin текущего сайта, фиксированные пути
лабораторного API, токен сессии из переданного обработчика, запрет переходов и
ограничение полного срока и размера ответа. Экземпляр привязывается к первой
сессии и отклоняет ответ, если сессия к моменту проверки изменилась; при выходе
всё равно нужно отменять операции и уничтожать экземпляр. Не сохраняет файлы, не выполняет
повторы сам и не подключён к приложению. Отмена и срок прекращают ожидание, но
сервер мог уже выполнить действие; при сбое обращаться с запросом как с
неопределённым, повторяя тот же пакет или подтверждение в рамках срока. При
недоверенном сертификате запрос отклоняется. Проверены лабораторный TLS, обмен
с реальным лабораторным API, подделки, обрывы, медленные и большие ответы,
перенаправления, отмена и смена сессии; браузерный VM и Node fetch не заменяют проверки в
настоящих браузерах, на телефонах и на Windows. Сертификат и ключ теста публичны
и непригодны для настоящего сервера. Перед реальным подключением нужны аудит,
работающий источник ключа и сессии, отзыв, безопасная Windows-граница и проверка
всего файла. Уязвимый сайт, изменённый сервером, может украсть ключ или токен.

`owner-file-check.js` — отдельный неподключённый эксперимент для сборки файла
в оперативной памяти (не более 8 МиБ) из проверенных частей. До чтения требует
`allowed === true` от вызывающего кода; это ещё не реальное согласие и не UI.
Контролирует длину, размер, постоянство метки версии и времени, затем вычисляет
SHA-256 всего результата и сравнивает с заранее заданным хешем. Проверяются и
пустые файлы. При ошибке собственный буфер очищается, при отмене дальнейшие части
не запрашиваются; зависшая внешняя операция может продолжаться и сохранять свои
копии. Возвращает только байты в памяти, а не файл на устройстве. Успех означает
совпадение с переданным хешем, но не подлинность файла: независимо доверенного
источника хеша пока нет, метка версии по метаданным не доказывает неизменности,
после проверки источник мог снова измениться. Нет скачивания, публикации,
проверки сохранённой копии, работы с большими файлами и восстановления после
сбоя. Перед настоящим сохранением обязательно спросить «Скачать файл на
устройство?», кроме явно включённой синхронизации; эта модель не выполняет
сохранение и не даёт разрешение на него. Проверены заглушки, шифрованный обмен в
памяти и браузерный VM, не реальный браузер или Windows.

`file-hash-candidate.js` — отключённая по умолчанию лабораторная подготовка
отметки файла источника: до 8 МиБ, частями, с проверкой размера и метаданных.
За один раз работает только одна проверка в одном экземпляре; если внешнее
чтение зависло и игнорирует отмену, экземпляр остаётся занятым до его завершения.
Опциональный обработчик `hashFile` в `read-service.js` позволяет передать эту
отметку в шифрованном ответе; по умолчанию операция запрещена. Клиент проверяет
пакет и формат до подтверждения, а сборка может дополнительно потребовать ту же
версию и время в каждой части, начиная с первой. Испытаны полный обмен на
фиктивном источнике, пустой файл, подмены, ошибки, отмена, предел и занятость.

Это **не доказательство подлинности и неизменности**: обе операции доверяют
одному источнику, метка версии может не заметить подмену, хеш может оказаться
результатом смешения нескольких состояний при изменении файла. Тест специально
показывает этот случай. Шифрование не спасает от подменённого источника или сайта,
принадлежность файла выбранной папке не доказана. Для реальной передачи нужны
безопасные дескрипторы и проверка на Windows, надёжная привязка и доверенный
источник ожидаемого хеша, контроль сохранённой копии, права, ограничения нагрузки
и независимый аудит. Ничего не подключено к пользовательскому приложению.
Для общих предварительных правил путей Node и браузера используется
`path-rules.js`; проверка строки не защищает от гонок и не заменяет Windows.
Проверены контекст браузера в VM и локальный HTTP/TLS с тестовыми данными, не
реальное приложение, установка или Windows. Если сервер подменяет код сайта,
это шифрование само по себе не предотвращает кражу ключа.

`relay.js`, `secure-channel.js` и `read-service.js` не подключены к обычному API,
браузеру или Windows-программе. Тест `test/local-pc-encrypted-flow.mjs`
прогоняет через эти компоненты зашифрованный запрос списка и чтения маленьких
частей файла в памяти; дополнительно проверяются чужой владелец, отзыв,
повреждённый пакет и запрет команд на удаление. Тест не использует HTTP.

- Relay не шифрует сам и полагается на вызывающий API для проверки сессии
  владельца, надёжного сохранения хеша токена и восстановления привязки после
  перезапуска. Очередь ограничена и живёт только в памяти. Идентификатор, время
  и размер пакета видны серверу. Не подключать relay к открытой сети без этих
  проверок и ограничений; пока он не зарегистрирован в сервере.
- Конверт использует стандартные HKDF и AES-GCM с разными ключами по
  направлениям; идентификатор и срок включены в проверяемые метаданные. Его
  тестируют на повреждение и совместимость Node/Web Crypto в среде браузера.
  Это не подтверждает безопасность всей системы. Хранение и передача ключей,
  проверка устройств и защита от повторного применения после перезапуска ещё
  не сделаны. Read-service хранит ответы на повторы только в памяти и поэтому
  допускает исключительно чтение. Вредоносный сервер, заменивший код сайта,
  тоже может обойти защиту на стороне браузера.
- Обработка больших папок и потоковая передача файлов в браузер ещё не реализованы.
  В лабораторном чтении частями метка версии позволяет обнаружить многие изменения
  файла между кусками, но это не хеш содержимого и не готовая проверка итоговой копии. Проверки путей пока не
  устраняют гонку подмены, особенно для junction/reparse points Windows.
  Доступ к реальным файлам из сети включать только после исправления и тестов
  на Windows 10. Никаких инструкций по установке готового помощника пока нет.


## Лабораторный HTTP и TLS

`experimental-api.js` подключается в `createApi` только явным тестовым параметром
`localPcExperimental: true` и только с файловым хранилищем; обычные `server.js`
и облако этот параметр не передают. Это не настройка для установки и не является
готовым интерфейсом для пользователя. Эксперимент содержит маршруты привязки,
опроса, пересылки шифрованных пакетов и отзыва, использует настоящую сессию
для владельца и отдельный случайный токен для помощника. Только хеш токена и
зашифрованная обёртка ключа должны сохраняться в базе. Есть экспериментальный код создания пары, но реальный установщик и безопасное
хранение ключа на Windows ещё НЕ реализованы. Удаление привязки блокирует
дальнейшие запросы агента; действующая сессия сама по себе не означает запрет
старого агента после смены пароля — это тоже надо решить до включения функции.

`agent-client.js` — один цикл опроса по HTTPS, не следует перенаправлениям и
по умолчанию проверяет сертификат. Срок установлен на весь HTTP-запрос, а не
только на время бездействия: медленный ответ не должен удерживать соединение
бесконечно. После отправки ответа требуется явное подтверждение сервера. Тест на
локальном HTTPS проверяет также остановку, неверные/слишком большие ответы и
отказ от перенаправления без передачи секрета другому адресу. Сигнал остановки
передаётся обработчику чтения и экспериментальному мосту Windows; мост пытается
остановить процесс PowerShell; если сигнал пришёл во время обработки, клиент не
начинает отправку запоздавшего ответа. Уже начатый запрос может попасть на сервер
даже после остановки. Если обработчик игнорирует сигнал, его работа может продолжиться в
фоне; даже попытка остановить PowerShell ещё не проверена на Windows. Системный
вызов и все стадии будущей записи/корзины пока не умеют гарантированно отменяться.
Повтор после отмены допускается только для лабораторного чтения, не для записи.
Пока клиент не запускается как служба, не устанавливается на ПК и использует лабораторные маршруты. Для тестирования
`test/local-pc-http.mjs` создаёт ограниченный тестовый HTTP/TLS сервер на
loopback, вызывает настоящий API с временной базой, проверяет изоляцию
владельцев, передачу списка и части файла, сбой сертификата, перезапуск и отзыв.
Тестовый сертификат и ключ в `test/fixtures/local-test-only-*` являются
публичными фиктивными данными и пригодны только для этого теста.

Лабораторный маршрут не проверен для эксплуатации; он не обещает гарантированной
доставки при перезапуске, не обеспечивает сквозную защиту от подмены сайта
скомпрометированным сервером и требует отдельного аудита приёмника,
контроля нагрузки, отзывов и Windows-защиты файлов. Нужно закончить реальную
привязку, устройство браузера, обработку больших файлов и протокол безопасной
передачи прежде, чем включать маршруты для обычного запуска.


## Установка и инструкция в мессенджере

Владелец требует, чтобы пошаговая инструкция и получение установщика были
доступны прямо из мессенджера. До любого скачивания на устройство требуется
вопрос «Скачать файл на устройство?». Скрипт не должен молча скачивать другие
компоненты. `setup-view.js` — пока не подключённый к приложению черновик окна;
тест проверяет, что без явного согласия вызов скачивания не происходит: только
буквальное `true` от подтверждения допускает вызов. Повторное нажатие блокируется,
а закрытие окна до ответа на вопрос отменяет запуск загрузки. Если родитель
убирает окно иначе, он обязан вызвать `disposeSetupView(root)`; удаление DOM само
по себе не отменяет ожидание. Уже начатый обработчик этот метод не останавливает;
сами обработчики, получатели и файлы здесь не проверяются. В черновике явно
сказано, что функция не готова; описание прав и будущей корзины не означает, что
они работают. Настоящих кнопки, установщика и инструкции по его запуску ещё нет. Реальное окно должно
оставаться в мессенджере, объяснять выбор одной папки, подключение ПК и отдельно
включаемую синхронизацию; нельзя показывать установку как работающую заранее.

`pairing.js` экспериментально создаёт секретный код, хеш токена и обёрнутый
личным ключом ключ обмена; он проверен на двух копиях личного ключа и отказах
при чужом ключе или другом адресе. Лабораторный API принимает первую привязку
в течение 10 минут и заменяет временный токен на новый токен ПК; одинаковый
повтор подтверждения допускается для восстановления после обрыва, но другая
попытка не проходит. Это ещё не законченная одноразовая установка: сохранение
при внезапной потере питания, безопасное хранение секрета на Windows,
принудительный отзыв при смене пароля и клиентский интерфейс не решены. Код
даёт доступ к ключу папки — его нельзя показывать другим или писать в логи.

При ручном отзыве лабораторный API сохраняет в тестовой базе номер устройства
со статусом `revoked`, убирает из текущей записи токены и обёрнутый ключ и не
позволяет повторно зарегистрировать тот же номер. Эта запись не занимает один
из 32 лабораторных неотозванных слотов. В общей сложности на одного владельца ограничено 1024
записи, включая отозванные: на пределе новые регистрации останавливаются, но
отозвать действующее устройство по-прежнему можно. При штатном закрытии и новом
открытии тестовой базы защита от повтора проверена. Фоновое сохранение может не
успеть при внезапной потере питания; старые резервные копии могут содержать
ранее выданные ключи, а удаление/восстановление учётной записи и многопроцессный
режим не проверены. Для лабораторного API теперь запрещено фоновое сохранение,
а каждый его запрос повторно сохраняет базу перед ответом, в том числе после
ошибки предыдущей записи. Если сохранение не удалось, ответ 503: изменение уже
может быть в памяти и повтор может вернуть отказ вместо первоначального успеха.
Это только эксперимент на одном процессе: синхронная запись всё ещё не означает
гарантированную сохранность после потери питания, текущие файлы/каталог не
обеспечивают проверенного fsync. Это не гарантированный постоянный отзыв и не
замена полноценной смене ключей и безопасному журналу. При смене пароля отзыва
пока нет.

`agent-coordinator.js` теперь требует адрес мессенджера отдельно от кода и от
сохранённых настроек и проверяет его как при новой привязке, так и при каждом
повторном запуске. Другой адрес или путь останавливает выполнение до чтения папки
и обращения к сети. Это не решает вопрос, как реально и безопасно получить
доверенный адрес: нельзя выводить его из самого кода подключения или из тех же
непроверенных настроек. Будущему установщику и интерфейсу нужен независимый,
понятный владельцу способ подтверждения; сейчас он не реализован. HTTPS и эта
проверка не защищают от подмены сайта самим сервером.


## Черновик помощника Windows

`agent-coordinator.js` испытывает порядок подключения: до подтверждения пары
новый токен и настройки сохраняются через предоставленное хранилище; при потере
ответа повторно проверяется тот же токен. Выбранный корень проверяется по
идентификатору каталога; при его замене подключение останавливается. Реальные
доступ к папке и сеть больше не выбираются автоматически: хранилище, проверка
корня, папка и транспорт обязательно задаются вызывающим тестом. Только явный
`null` от хранилища разрешает начать новую привязку; некорректная запись не
открывает папку или сеть. Проверяется точный набор полей текущей версии настроек.
На поддельном хранилище проверен повтор после ситуации, когда запись произошла,
но её ответ потерялся. Реальную долговечность записи это не подтверждает.
Хранящийся между
опросами транспорт обращается к папке, проверенной в текущем опросе, а вне
опроса новая операция чтения отклоняется. Лабораторные `anchorFolder` и
`folder.js` остаются небезопасными для настоящих файлов; повторная проверка не
устраняет гонки и не заменяет Windows-проверку reparse points.

`windows-vault.ps1` и `windows-vault.js` — черновик хранения через Windows
DPAPI текущего пользователя, с передачей настроек через каналы процесса, без
секретов в аргументах. `windows-wizard.ps1`/`.js` — черновик локального окна
выбора папки и ввода кода; адрес сервера и выбранная папка выводятся для
подтверждения. Тесты обёрток работают с поддельным процессом. Реальные DPAPI,
права папки, сохранение при внезапном сбое, форма и поведение идентификаторов
каталога на Windows 10 ещё НЕ проверены. Обёртка отклоняет неверные ответы;
скрипт теперь различает явное отсутствие файла и иные ошибки чтения с помощью
`GetAttributes`, отказывая при каталоге или reparse-point вместо файла. Это
изменение на Windows не запускалось; оно НЕ доказывает защиту всех предков и
гонок. Удалённый файл настроек всё ещё не отличим от первой установки: нужен
отдельный надёжный признак уже существовавшей привязки и восстановление.
Ни эти файлы, ни код из ветки не
являются готовой программой или установщиком; они не скачивают Node.js или что-либо
ещё и не запускаются при обычной работе мессенджера.

Лабораторный тест HTTPS проверяет создание кода, привязку, опрос,
чтение файла, отказ чужому пользователю и отзыв вместе; вместо DPAPI используется
память, вместо Windows — тестовая система. Для выпуска всё равно нужны настоящие
безопасный установщик, встроенная инструкция/кнопка, самостоятельный запуск и
остановка помощника, полноценная интеграция браузера, а также аудит и
проверка реальной Windows 10.


`windows-helper.js` и `agent-runner.js` — неустановленные экспериментальные
заготовки. Прямой запуск `windows-helper.js` принудительно останавливается с
сообщением «ещё в разработке», без открытия хранилища, папок или сети; включающего
флага нет. Импортируемая функция помощника работает только с явно переданными
зависимостями для теста — передача настоящих компонентов не делает её безопасной.
Установка и автозапуск ещё не сделаны. Проверены остановка, повтор после потери
связи и отказ после отзыва на тестовых объектах. Координатор проверяет сигнал
после создания транспорта и ответа, не начинает привязку после остановки и не
подтверждает подключение при некорректном ответе опроса. Цикл показывает
`online` лишь после завершённого опроса с ожидаемым результатом; это не означает
синхронизацию. Чтобы избежать параллельных действий, остановка ждёт завершения
текущего тика: игнорирующая сигнал зависимость может задержать её бесконечно.
Запрос или сохранение, уже начатые до остановки, могут закончиться позднее;
тесты не подтверждают надёжную остановку сторонних обработчиков или Windows.
Корневой каталог проверяется по
идентификатору, но вложенные пути всё ещё подвержены гонкам.
Требуется безопасное открытие Windows-файлов через проверенные системные
дескрипторы и настоящее испытание на Windows до выдачи доступа.


`test/local-pc-windows-real.mjs` предназначен для проверки на чистой
виртуальной Windows CI: синтаксис PowerShell, DPAPI и права папки. Даже в CI
проверка DPAPI запускает копию скрипта, где путь к хранилищу подменён на новый
временный каталог; настоящий `SEGA-CHAT/LocalDisk` она не использует. Это не
точная проверка выбора настоящего пути и не основание запускать её на данных
владельца. Для формы добавлена проверка чтения русской строки парсером Windows
PowerShell. Запуск на GitHub Actions пока недоступен: GitHub App отказал в праве
создавать workflow. Ни одна из этих проверок на Windows ещё не выполнялась.
Виртуальная Windows Server не заменит пользовательский тест на Windows 10;
доступ к файлам и установщик по-прежнему не готовы.

Для русских строк Windows PowerShell 5.1 скрипты и C#-источник сохранены в UTF-8
с BOM; `test/local-pc-windows-encoding.mjs` проверяет байты и строки на любой
платформе. Это статическая проверка, не запуск формы или компиляция на Windows.

`windows-safe-folder.cs`, `windows-safe-folder.ps1` и
`windows-safe-folder.js` — изолированный эксперимент для чтения на Windows,
**не подключённый к помощнику и не пригодный для настоящих файлов**. Он пытается
удерживать открытыми предков без разрешения переименования и удаления, отклонять
reparse points и файлы с несколькими жёсткими ссылками, проверять идентификатор
корневой папки и читать файл без разрешения параллельной записи. Метка версии
основана на метаданных и не является хешем содержимого. Подмена содержимого при
сохранении прежних метаданных не исключена. Число жёстких ссылок само по себе
не доказывает происхождение файла: если другое имя удалили, остаётся одна ссылка.
Это не гарантирует безопасность и не
решает запись, корзину или синхронизацию. Есть ограничения на размер запроса;
перед подключением к остальным компонентам нужно согласовать размеры частей.
Мост теперь отклоняет корни с `.`/`..`, пустыми промежуточными компонентами и
смешанными разделителями вместо молчаливой нормализации в другую папку; также
проверяет полную длину каждого полученного куска, границу всего пути, формат
элементов и одинаковые имена в обоих режимах списка. Срок внешнего процесса
ограничен 100–60000 мс. Это проверки JavaScript на поддельном PowerShell, не
проверка безопасности самой Windows, полноты списка или подлинности данных.
Сторонний Linux SDK .NET 2.0 не запустился из-за отсутствующей `libunwind.so.8`.
Вместо этого его Roslyn 2.3.2 запущен на временном .NET Core 3.1.23 с OpenSSL
1.1: исходный C# скомпилирован в библиотеку с библиотеками 3.1.23; нарочно
испорченная копия получила ошибку компиляции. Инструменты и результат находились
только в `/tmp`. Это не проверка компилятора Windows PowerShell/Add-Type, Win32
или выполнения и безопасности; нужны чистая Windows и независимый аудит.

В черновик добавлен `HashLocked`: файл до 8 МиБ открывается один раз без
разрешения обычной параллельной записи/удаления, целиком читается и хешируется
до закрытия этого дескриптора; метаданные сверяются до и после. Экспериментальный
мост предоставляет метод только с `enableLockedHash: true`; в помощнике он не
включён. Тест с поддельным PowerShell соединяет его с зашифрованной сверкой;
это не проверка реальной Windows. После закрытия дескриптора файл может
измениться, чтение частей открывает его заново. Сохранение метаданных, работа
отображений в память и особых файловых систем, путь и происхождение данных не
доказаны; такой хеш не является атомарным снимком или гарантией подлинности.
Компиляция и проверка на настоящей Windows и независимый аудит обязательны.

Отдельный выключенный по умолчанию `SnapshotLocked` экспериментирует с другим
вариантом: при одном открытии до 8 МиБ копируются в память, и хеш вычисляется
именно по этим байтам. Мост дополнительно сверяет длину, кодирование и хеш,
предоставляет только копии частей и через ограниченное время закрывает свою
копию. В одном экземпляре моста одновременно допускается одна копия либо её
создание. Требуется явный `enableLockedSnapshot: true`; к помощнику и сети этот
механизм не подключён. Файл на устройство не скачивается и не публикуется.
Изменение источника после успешного создания не изменяет байты этой копии, но
её создание всё равно не доказывает атомарность и происхождение данных. Хеш не
защищает от подменённого процесса или сайта. Данные проходят открытым текстом по
локальному каналу PowerShell/Node и временно существуют в нескольких буферах и
строках; очистка закрывает и заполняет нулями только собственный буфер Node, не
гарантирует очистку всех копий или памяти ОС. Отмена может вернуть управление до
фактической остановки процесса; нельзя гарантировать, что на Windows он завершён.
Временной лимит и ограничение одного экземпляра не являются общесистемной
блокировкой. Проверены заглушки, предел и повреждения; будущий Windows-тест
расширен, но C# компилировался только в Linux и на Windows не запускался.

`snapshot-session.js` и лабораторные операции `snapshotOpen`, `snapshotRead`,
`snapshotClose` передают части одной такой копии через зашифрованный обмен.
Подключение сессии к `read-service` должно быть явно передано; по умолчанию
операции выключены. Случайный номер, максимум одна копия на экземпляр и срок
ограничивают эксперимент, но не заменяют проверку прав и общесистемные лимиты.
При закрытии очищается только область поставщика; ошибки очистки блокируют
экземпляр, но зависший внешний обработчик может продолжать работу. Закрытие
повторяется для последней закрытой копии, пока есть отметка в памяти. При
перезапуске, истечении или сбое продолжить не гарантируется; автоматической
загрузки и восстановления нет. Уже выданные байты отозвать нельзя: зашифрованные
ответы также могут временно оставаться в кэше агента или очереди после закрытия.
Проверен обмен на поддельном поставщике и поддельном PowerShell, включая обрывы,
срок, отказ при повреждении, пустой файл и полную часть. Это не доказывает, что
исходная Windows-копия была атомарной, правильно привязанной или доверенной.

`owner-snapshot-transfer.js` — неподключённая последовательность ручного
получения **только в память**. До первого запроса вызывает переданное извне
подтверждение и продолжает только при точном `true`; настоящего окна с вопросом
ещё нет. Открывает копию, получает проверенные части с ограниченными повторами
того же запроса, сверяет весь хеш и пытается закрыть копию до выдачи результата.
При отмене или ошибке закрытие известной копии пытается выполнить отдельно, с
ограниченным временем; если оно не подтверждено, результат не выдаётся и ошибка
очистки не скрывается. Если ответ на открытие потерян до получения номера, закрыть
копию этим кодом невозможно — остаётся ждать истечения срока на компьютере.
Уже начатый внешний обработчик может продолжать работу, а зашифрованные ответы
могут оставаться в очереди/кэше. Вызывающий код обязан обеспечить реальные
права, подлинное согласие, безопасный транспорт и отмену при выходе пользователя.
Не используется для синхронизации, не сохраняет файл, не работает с файлами
больше 8 МиБ и не доказывает подлинность/атомарность Windows-источника. Даже
после успеха настоящее сохранение потребует отдельной безопасной реализации;
перед ним нужен вопрос «Скачать файл на устройство?» (исключение — явно
включённая автоматическая синхронизация).

Проверены отказы до первого запроса, отмена, потери ответов, подмена, проверка
частей и полного хеша, закрытие, срок и ошибки очистки. Дополнительно в Node
через локальный TLS испытан настоящий лабораторный API с фиктивной копией; VM и
Node fetch не являются настоящим браузером, Windows не проверена.

`owner-list-request.js` и `owner-disk-view.js` с отдельным CSS — неподключённый
черновик окна просмотра. Окно открывает папки и возвращается назад внутри диска,
показывает «Нет соединения» при явно сообщённом отсутствии сети, требует
буквальное согласие на вопрос «Скачать файл на устройство?» до начала пробного
получения и не делает запись/скачивание. Оно прямо сообщает, что функция не
готова; после проверки собственный полученный буфер пытается очистить. Закрытие,
внешнее `dispose` и переход отменяют ожидание и блокируют поздние изменения
окна. Внешний обработчик при этом может продолжать работу; гарантированной
очистки всех копий памяти нет. При возвращении сети автоматического повтора нет.

Окно принимает действия извне: настоящий источник, проверку пользователя и прав,
безопасность транспорта и честность результата обязан обеспечить вызывающий код.
Список не доказывает полноту и не может использоваться для синхронизации или
удаления. CSS и DOM проверены в jsdom и VM, включая имена, отказ от согласия,
вложенные папки, устаревшие ответы, закрытие и отключение; настоящий браузер,
адаптивность на телефоне и Windows не проверены. Окно не подключено к мессенджеру,
не заменяет установку и не предоставляет синхронизацию, запись или корзину.

`file-preview-view.js` и CSS — неподключённый черновик просмотра поверх пробного
окна папки. При переданном `loadPreview` нажатие файла открывает просмотр, а
отдельная кнопка «Скачать» по-прежнему требует согласия и ничего не сохраняет.
Закрытие просмотра возвращает к той же папке; закрытие диска отменяет просмотр.
Фото PNG/JPEG/GIF/WebP переключаются кнопками, стрелками клавиатуры и жестом в
сторону; формат определяется по расширению и сигнатуре, не поддерживается SVG.
Документы только известных текстовых расширений читаются как UTF-8 или UTF-16
с меткой порядка байтов, отображаются через `textContent` на белом фоне. Для
неподдерживаемых форматов/кодировок и двоичного содержимого показывается понятная
надпись; DOCX/PDF и другие сложные форматы пока не разобраны. Строгая декодировка
и проверка управляющих символов не доказывают смысловой правильности текста и не
исправляют уже испорченное содержимое. Ограничение размера — 8 МиБ.

Просмотр не скачивает и не сохраняет файлы. `loadPreview` должен получать только
разрешённые, проверенные байты и передавать владение буфером просмотру: при
завершении/запоздании буфер заполняется нулями, а временный blob-адрес
отзывается, но все копии в браузере или ОС очистить не гарантируется. Закрытие
не обязательно останавливает внешнюю зависимость. Проверены jsdom/VM, пробные
файлы, XSS-разметка, ошибки кодировок, переключение и отмена; реальный браузер,
жесты на телефоне, декодирование изображений и Windows не проверялись. При
настоящем подключении нужны безопасный источник, права и аудит. Этот черновик не
включён в мессенджер.

Тест моста использует заглушку процесса и не проверяет Windows. C# скомпилирован в Linux, но не в Windows PowerShell. Тест для чистой Windows CI дополнен
проверкой обычного чтения, замены корня, junction, жёсткой ссылки, отдельного
отказа `listFailOnSkipped` для junction и жёсткой ссылки, хеширования пустого
и обычного файла, отказа для большого файла, ссылок и открытого на запись файла,
и небольшой попыткой
подмены вложенной папки во время чтения. Он ещё **не запускался на
Windows** и не доказывает отсутствие гонок; необходимы компиляция на Windows, подробные
испытания на Windows 10 и независимый аудит. До этого нельзя открывать сетевой
доступ к реальным файлам через любой из экспериментальных вариантов.

## Учебная модель восстановления после обрыва

`recovery-journal.js` — отключённая модель записи одной условной операции
копирования, переименования или перемещения в корзину. Перед внешним действием
вызывающий код может сохранить состояние `uncertain`; после перезапуска оно
требует проверки назначения, а не автоматического повтора. При ошибке сохранения
экземпляр переходит в неизвестное состояние и запрещает дальнейшие переходы.
`confirmed` означает только отметку вызывающего кода, а не доказанное выполнение.

Модель не выполняет операции, не хранит журнал сама и не предоставляет разрешение
на действия. Она полностью доверяет переданному `save` и сохранённым данным;
нет fsync, транзакций, аутентификации, блокировки процессов, восстановления базы,
проверки корзины или защиты от сбоев питания. Тест имитирует перезапуск и обрыв
в памяти, в том числе потерю ответа на сохранение и параллельные вызовы.
Дополнительный тест останавливает отдельный процесс после завершённой записи во
временный файл и читает её заново; обрезанный JSON вызывает ошибку. Тестовое
хранилище не атомарно и не вызывает fsync: обрыв во время записи, сбой питания
и целостность при повреждении диска им не проверены. Для
реальной синхронизации необходимы отдельное устойчивое хранилище, проверка каждой
стороны, согласованный протокол и испытания на Windows и облаках.

## Черновик проверки передачи по частям

`verified-transfer.js` работает только с переданными извне источником и
**временной** областью. Он не открывает файлы, не скачивает их и не публикует
копию. До обращения к источнику требуется явный флаг разрешения; настоящая
проверка согласия пользователя при скачивании или включённой синхронизации ещё
не подключена. На каждом шаге проверяются размер и версия источника; по
окончании проверяется полный SHA-256 переданных данных и результат повторной
проверки записанной временной копии. В случае ошибки или остановки вызывается
очистка; ошибка очистки не скрывается. Один объект временной области теперь
принимается только один раз, даже после успеха, остановки или неудачной очистки:
повторное использование не вызывает запись или очистку и не мешает первой
попытке. Для новой попытки нужна новая изолированная область. Это проверка
идентичности объекта в одном экземпляре модуля, НЕ блокировка файла: разные
объекты, модули или процессы всё ещё могут указывать на одну область. Настоящий
исполнитель должен обеспечить исключительное владение и восстановление сам.
При отмене ожидание зависшего чтения источника прекращается, после чего область
очищается; источник может продолжить работу и по контракту не должен иметь к ней
доступа. Запись или проверку области, начатую до отмены, нужно дождаться перед
очисткой: зависшая зависимость может задержать её бесконечно. Остановка не
гарантирует отмены системного вызова. Тест дополнительно использует изолированные
временные файлы на Linux: успех, обрыв чтения, повреждение, ошибка записи и
неудачная очистка; исходник и заранее занятый файл остаются нетронутыми. Это
тестовый адаптер, не реализация безопасной временной области на Windows, не тест
потери питания или публикации. Дополнительно `createFolder.read` соединён с
передачей на временных Linux-файлах: успешная копия совпадает с исходником,
изменение исходника того же размера или переименование между частями вызывает
ошибку и очистку области. Метки и эти тесты не исключают подмены, гонки или
изменения после проверки; `folder.js` небезопасен для сетевого доступа. Отдельно тест демонстрирует, что лживый `verify`
может скрыть повреждение, если не перечитывает реально записанные байты.

Сами флаг разрешения, ожидаемый хеш и методы временной области предоставляются
вызывающим кодом и не являются доказательством их надёжности. Временная область
должна быть изолирована от оригиналов, принадлежать только одной передаче,
реально перечитывать записанные байты и не допускать их подмену. Проверка
источника до публикации должна обнаруживать и более поздние изменения.
При неверных аргументах до начала передачи вызывающий
код отвечает за очистку области, если создал её заранее. После успешной проверки
файл всё ещё НЕ опубликован: реальная запись, повторная проверка обоих ПК,
безопасная замена, корзина, сохранение при сбое и восстановление не реализованы.
Проверка включена в цепочку тестов: заглушки проверяют обрыв, порчу и отмену;
отдельно пройдена передача небольшого файла по зашифрованным сообщениям в памяти.
Это не проверка Windows. Лабораторная очередь допускает до восьми одновременно
ожидающих запросов; в режиме только для чтения владелец может подтвердить
получение ответа через `ack`, освободив место после проверки сообщения. Номер
подтверждённого или истёкшего запроса хранится до конца максимально допустимого
срока его зашифрованного пакета с допуском часов: в текущих настройках 150001 мс
от приёма. Это справедливо только для правил лабораторного API и неизменных часов;
сам relay не проверяет содержимое или срок пакета. Подтверждение истёкшего без
`ack` ответа не выдаётся за успешное. Число живых запросов и сохранённых
отметок вместе ограничено 1024 на устройство: при переполнении новые
запросы отклоняются, не вытесняя старые отметки. Повтор подтверждения допустим
до истечения отметки. Пройден тест девяти последовательных частей в памяти и
лабораторные HTTP-проверки подтверждения. Очередь и отметки не переживают
перезапуск или отзыв устройства; это не полная защита от повторов. Ограниченный
кэш ответов агента и отсутствие полноценного протокола
восстановления пока препятствуют практической передаче больших файлов. Эти
механизмы нельзя использовать для записи или удаления.
